# ADR-0008：用 `round_id` 作为轮次关联键

- 状态：已采纳
- 相关：`docs/requirements/multi-turn-backend.md §2.1 / §3.2`、`docs/schema.sql`、`.scratch/multi-turn-conversations/spec.md`

## 背景

原设计没有显式的「轮次」字段：用户消息与助手消息各自是一条 `message` 记录，只能靠自增 `id` 相邻来推断「这一问对应这一答」。这个推断在正常路径下看似成立，但以下情况都会错配：

- 助手消息落库失败或延迟，导致两条消息之间插入其他记录；
- 流式任务异步提交，完成顺序与受理顺序不一致；
- 用户重试或重复提交，产生额外的助手消息；
- 软删除、补洞或历史数据修复改变了自增序列的连续性。

一旦相邻关系断裂，历史回放、引用定位与「一轮一问一答」的约束都会失效，而且错误是静默的：界面仍能渲染，只是配错了答案。

## 决策

采用显式轮次键 `round_id`：

- 同一轮的用户消息与助手消息写入同一个 `round_id`；
- 数据库加 `UNIQUE (conversation_id, round_id, role)`，从结构上保证一轮最多一条 `USER`、一条 `ASSISTANT`；
- `round_id` 在受理提问时生成，同时通过 SSE `meta` 回传前端；
- 不采用 `reply_to_message_id`，也不两者并用。

## 影响

- 前端聚合「问题—回答—引用」必须按 `roundId` 分组，禁止用数组下标或相邻顺序配对；历史接口可以继续扁平返回。
- 一轮的完整性由数据库约束兜底，应用层不需要再写「是否已有回答」的防御性判断。
- `round_id` 只在本会话内有意义，不承担跨会话唯一性；查询与索引都需带 `conversation_id`。
- 若未来引入「一轮多回答」或「分支重答」，需要重新设计该唯一约束，而不是在现有字段上打补丁。
