# 后端修改需求：为新 React 前端补数据

> 交接对象：负责 `lender-assistant` 后端实现的会话
> 目标：让新前端（文档管理 + 知识库对话）拿到它必须的数据，**不改检索算法、不改问答链路语义**
> 依据：前端 PRD 已定稿，以下每一项都对应一个前端界面元素；不做超出此清单的改动

## 1. 变更清单（共 4 项，全部为增量，不改既有出参语义）

### B1 新增：文档切片分页查询接口

**动机**：前端的"查看切分信息"抽屉必须有数据源，否则需求无法实现。

- 新接口：`GET /api/admin/documents/{docId}/chunks?page=1&size=20`
- `page` 从 1 开始，默认 1；`size` 默认 20，取值范围 1–100，越界由 Service 归一（`TopKUtils` 同风格工具方法）
- 走全局 `ApiResponse` 包装，**不要**加 `@RawResponse`
- 出参 DTO（新建，放 `rag/vo/response/`，按约定以 `Response` 结尾）：

```java
public record ChunkPageResponse(String docId, int page, int size, long total,
                                List<ChunkItemResponse> items) {}

public record ChunkItemResponse(Long chunkId, Integer index, String sectionPath,
                                Integer charCount, String content) {}
```

- 注意：`chunkId/index/charCount` 用**包装类型**（MyBatis `<constructor>` 映射的既有教训，见 `DocSummary` 注释）
- Mapper 新增方法（`DocChunkMapper.java` + `DocChunkMapper.xml`）：

```java
List<ChunkItemRow> listChunkPage(@Param("docId") String docId,
                                 @Param("limit") int limit, @Param("offset") int offset);
long countByDoc(@Param("docId") String docId);   // 已有同名方法，确认签名后可复用
```

```xml
<select id="listChunkPage" resultMap="chunkItemMap">
    SELECT id, chunk_index, section_path, char_count, content
    FROM doc_chunk
    WHERE doc_id = #{docId}
    ORDER BY chunk_index
    LIMIT #{limit} OFFSET #{offset}
</select>
```

- `docId` 不存在时：不要返回空列表装作成功，抛 `BizException` + 新增错误码（如 `DOC_NOT_FOUND`），由全局异常处理转成 `code/msg`
- 实体类里**不要**带 `embedding`（1024 维字符串会让响应从 KB 级膨胀到 MB 级）
- 验收：`GET /api/admin/documents/huaxin_corp_api_v1/chunks?page=2&size=10` 返回 10 条、`total` 正确、`content` 为原文

### B2 扩展：文档概览补 3 个字段

**动机**：前端文档列表要显示原始文件名、总字符数、最近入库时间；现有 `DocSummary` 只有 3 个字段，其余全是前端编造。

- 表结构：`doc_chunk` 增列（写进 `docs/schema.sql`，schema 为唯一事实源，见 ADR 0006）

```sql
ALTER TABLE doc_chunk ADD COLUMN ingested_at timestamptz NOT NULL DEFAULT now();
```

  - `replaceDocument` 是"删后插"，新行自动带 `now()`，语义正好是"最近一次入库时间"，**不需要**手写赋值
  - 存量行会统一变成迁移时间，属已知偏差，不需回填
- `DocSummary` 改为（字段顺序即 `<constructor>` 的 arg 顺序，必须同步改 `docSummaryMap`）：

```java
public record DocSummary(String docId, String docTitle, String sourcePath,
                         Integer chunkCount, Long charCountTotal, String ingestedAt) {}
```

- `listDocuments` SQL 改为：

```sql
SELECT doc_id, doc_title, MAX(source_path) AS source_path,
       COUNT(*) AS chunk_count, SUM(char_count) AS char_count_total,
       TO_CHAR(MAX(ingested_at), 'YYYY-MM-DD HH24:MI:SS') AS ingested_at
FROM doc_chunk
GROUP BY doc_id, doc_title
ORDER BY doc_id
```

- `ingestedAt` 用 `String`，避免给前端引入时区/序列化歧义
- 验收：`GET /api/admin/documents` 返回 6 个字段，旧 `index.html` 用字段名取值不受影响（只多不少）

### B3 扩展：SSE `sources` 事件补检索明细

**动机**：前端"检索过程"侧栏要展示双通道命中与 RRF 分数；现在只能拿到文档名和章节路径。数据全在 `SearchItemResponse` 里，只是没映射进 `QaSourceResponse`。

- `QaSourceResponse` 改为：

```java
public record QaSourceResponse(Integer idx, String docTitle, String sectionPath,
                               Long chunkId, String content, Double vectorDistance,
                               Integer keywordHits, Boolean bothChannels, String rrfScore) {}
```

- `QaServiceImpl.streamAnswer()` L94-99 映射处直接取 `hit` 的对应字段，**不要**为了取字段再查一次库
- `content` 传原文（单条切片量级小），前端只做 2 行截断展示，点击展开
- 事件协议本身不变：仍是 `sources → delta* → done`，**不新增事件类型**，不加 `retrieval` 之类的中间事件
- 验收：`curl -N -X POST localhost:8080/api/qa -H 'Content-Type: application/json' -d '{"question":"首套贷款成数上限","topK":4}'`，`sources` 数组每项含 9 个字段，`rrfScore` 为 5 位小数字符串

### B4 校验与错误语义对齐（小改）

- `POST /api/admin/documents`：`docId` 增加合法性校验（非空、长度 ≤ 64、仅 `[a-zA-Z0-9_-]`），非法直接 `BizException`，不要等 SQL 报错
- 上传失败（解析器不支持、嵌入服务超时）要在响应里可区分：沿用现有异常处理即可，**不新增** `status` 字段——前端按 HTTP 状态 + `code` 区分，不依赖"解析中"这类状态机
- 明确保留：`topK` 默认值来自 `SearchConstants.DEFAULT_TOP_K`，前端可选传

## 2. 明确不做

- 不做查询改写、不做 rerank、不改 RRF 融合逻辑与阈值默认值
- 不做会话持久化 / 多轮上下文（前端按单轮实现）
- 不做原文件存储、下载、PDF 预览（只存解析后的文本）
- 不做文档重命名、更新时间之外的元数据（部门、页数等业务字段不进知识库表）
- 不动阶段 4/5 的字段映射抽取与代码草稿生成链路，也不动 `index.html`

## 3. 落地注意

- 生成/修改类操作集中到 `DocumentService` / `SearchService` 实现，Controller 只做编排，命名沿用 `Service` / `Impl` 约定
- 切片分页是纯读，不需要 `@Transactional`；`replaceDocument` 保持既有 `@Transactional`
- 改 `DocSummary` / `ChunkItemRow` 这类 record 构造参数后，**同步改所有调用方与 `src/test`**（历史教训：漏改 `SearchServiceTest` / `QaServiceTest` 导致假绿）
- 收尾跑一次 `mvn test`（必要时先删 `target/test-classes` 防增量编译假成功）
- 收尾自检建议按顺序：上传一个 docx → 列表看 6 字段 → 翻第 2 页切片 → 提问看 `sources` 明细
