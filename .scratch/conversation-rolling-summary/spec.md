# 会话级滚动摘要 · 规范文档（Spec）

> 来源：`docs/prd/conversation-rolling-summary.md`（已定稿，Q1–Q5 按推荐口径落地；含需求 1 窗口参数 10 轮 / 8000 字符决策）
> 定位：把已定需求翻译成可直接实现的规范。**不重新讨论决策**，如有冲突以 PRD 与 [ADR-0020](../../../docs/adr/0020-rolling-summary-boundary-as-round-id.md) 为准并在评审中提出。
> 状态：待评审，评审通过前不写代码。
> 术语口径以 `GLOSSARY.md`「多轮对话词」为准：完整轮、回放窗口、滚动摘要、摘要覆盖边界。

---

## 1. 问题陈述（Problem Statement）

从使用者视角看：

- 长会话深聊时，模型只能看到回放窗口内的最近几轮。第 1 轮提到的客户号、产品编码等关键事实，到十几轮之后追问时模型已经「看不见」，回答丢失上下文且用户无从知晓——早期信息是无声消失的。
- 用户打开历史会话时，没有任何提示告诉他「这段对话的更早部分只以梗概形式参与回答」。

从维护者视角看：

- 回放窗口实际保留轮数是「轮数上限」与「字符预算」两个上限取小的结果，无法用固定轮数描述「哪些轮被裁掉了」；任何按配置数字（如「6 轮之前」）驱动的逻辑都会在参数调整时静默错位。
- 窗口参数随时可能调大或调小：调大后旧轮次回归窗口会与已注入的摘要重复；调小后会出现摘要没盖住的新间隙。没有一套明确的规则，这两个方向都会产生重复或遗漏。

## 2. 解决方案（Solution）

消息继续全量落库（现状不变），在回放策略之上叠加滚动摘要：

1. **回放窗口**：每轮问答装配历史时实算窗口起点（轮数上限 10、字符预算 8000，从最旧一轮整轮丢弃），窗口外被裁轮次恒为完整轮序列的最旧连续前缀。
2. **滚动摘要**：一轮回答正常收尾后，异步检测「被裁前缀」是否比库中已存摘要边界更长；是则把「现有摘要 + 新被裁轮次原文」滚动合并，调模型生成新摘要（上限 500 字符），与覆盖边界一起原子写回会话表。
3. **精确边界**：会话表新增 `summary` 与 `summary_boundary_round_id` 两列，边界记「被摘要覆盖的最后一个完整轮的 roundId」，绝不记轮数数字（ADR-0020）。
4. **注入去重**：KNOWLEDGE 轮装配时，仅当边界轮严格早于本轮窗口最旧轮才把摘要注入 system 段尾部（宁缺勿重）——窗口调大后旧轮次自然回归，不会与摘要重复。
5. **用户可见**：历史消息接口带出摘要两字段；前端在消息列表顶部展示轻量提示条（仅展示、无交互）。

需求 1（窗口参数）随本规范落地：`history-max-rounds` 6→10、`history-max-chars` 2000→8000，纯配置变更。

## 3. 用户故事（User Stories）

### 上下文完整性

1. 作为问答用户，我想在连续追问 8 轮以上时模型仍能引用第 1 轮提到的信息，以便深聊不用反复自我介绍背景。
2. 作为问答用户，我想让窗口外的早期对话以梗概形式继续参与回答，以便早期结论（如已确认的产品线）在长会话后段仍被尊重。
3. 作为问答用户，我想让摘要明确标注「仅作背景参考」，以便它不会与当前召回资料竞争、被当成权威依据。
4. 作为问答用户，我想让「那二套呢」这类指代解析可用的历史范围随窗口扩大而变大，以便追问更自然。
5. 作为问答用户，我想让摘要不参与检索 query 改写，以便检索仍然基于我的原话，不被模型转述带偏。
6. 作为问答用户，我想让 PLAN 轮合成保持现状（不重放完整历史、不注入摘要），以便计划流程行为不变。
7. 作为问答用户，我想让失败轮次（FAILED/STOPPED）与固定提示轮（rule）继续被排除在外，以便摘要和回放都只反映真实完成的问答。

### 参数与成本

8. 作为部署者，我想用环境变量覆盖历史窗口两个参数与摘要长度上限，以便不同环境按需调整而不改代码。
9. 作为部署者，我想让短期会话的成本不因窗口上限调大而增加（按实际字数计费），以便放心采用 10 轮 / 8000 字符。
10. 作为维护者，我想让进一步控成本时只降字符预算、不降轮数，以便短追问链的质量保障不随省钱动作一起缩水。

### 摘要生命周期

11. 作为问答用户，我想让摘要生成不拖慢我的回答（异步执行），以便问答延迟不变。
12. 作为问答用户，我想在摘要生成期间立即追问时不遇到「会话忙」错误，以便摘要任务让路、不干扰正常问答。
13. 作为问答用户，我想让被跳过的摘要任务在下一轮完成后自动补齐，以便摘要最终总会追上被裁进度，无需人工干预。
14. 作为问答用户，我想让摘要生成失败时旧摘要保留、回答链路完全无感，以便模型故障不产生任何用户可见的退化。
15. 作为维护者，我想让每次摘要调用留痕（scene=summary）并走熔断重试，以便与其他模型调用一样可观测、可降级。
16. 作为维护者，我想让摘要正文超限时硬截断而不是追加二次模型调用，以便摘要成本有硬上限。
17. 作为维护者，我想让摘要与覆盖边界在同一行原子更新，以便任何时刻读到的摘要与边界自洽。
18. 作为维护者，我想让摘要 prompt 遵守与问答同构的铁律（只依据输入、不编造），以便摘要错误不成为幻觉新源头。
19. 作为维护者，我想让摘要任务独占一个小型单线程池且有界队列拒绝时静默跳过，以便摘要慢不反压回答主链路。

### 配置变更适应性

20. 作为维护者，我想让窗口参数调大后旧轮次自然回归窗口且不与摘要重复注入，以便调参不需要任何数据迁移或摘要重算。
21. 作为维护者，我想让窗口参数调小后的间隙轮在下次合并时补进摘要，以便调小不产生永久性的上下文盲区。
22. 作为维护者，我想让边界判定每轮从数据库实算而不是引用配置数字，以便两个上限无论谁先到、参数怎么改，逻辑都成立。

### 用户可见性

23. 作为问答用户，我想在打开超过窗口的会话时看到顶部提示条「更早对话已折叠为摘要」，以便知道早期内容以梗概参与。
24. 作为问答用户，我想在未超窗口的会话里看不到任何提示条，以便界面不为不存在的功能添噪。
25. 作为前端开发者，我想让历史接口用 `summary` 非空与否作为提示条的显示条件，以便前端不需要自己推断窗口状态。

## 4. 实现决策（Implementation Decisions）

### 4.1 模块划分

| 模块 | 职责 |
|---|---|
| 会话领域 | 摘要服务（边界实算、滚动合并、模型调用、写回）、异步触发编排、摘要客户端（client 层） |
| 会话装配 | `ConversationHistoryAssembler` 扩展：窗口起点实算、可注入摘要判定，返回值新增摘要 |
| 公共常量 | 新增 `LlmScene.SUMMARY`（scene 取值清单同步 llm_call_log 注释） |
| 模型网关 | 复用 `ResilientLlmExecutor`（留痕 + 熔断 + 重试）；摘要走非流式调用，超时与路由/计划同构（Reactor `timeout` 复用代码常量 `NON_STREAM_TIMEOUT`，10s） |
| 数据访问 | 会话表两列、Mapper 读写、实体字段同步 |
| 对外接口 | 历史消息接口响应新增 summary 两字段 |
| 配置 | `rag.qa.history-max-rounds:10`、`history-max-chars:8000`、`rag.qa.summary.max-chars:500` |

### 4.2 数据模型

会话表新增两列（幂等 `ADD COLUMN IF NOT EXISTS` 迁移，与 route/execution_plan 先例一致；schema 变更同步回写 `docs/schema.sql`）：

- `summary TEXT NULL`：滚动摘要正文，NULL 表示尚无摘要。
- `summary_boundary_round_id TEXT NULL`：被摘要覆盖到的最后一个完整轮的 roundId；与 summary 同写同空。

每列带 `COMMENT ON COLUMN`（schema.sql 惯例，边界列注明「与 summary 同写同空」）。

**写回规则**：独立 UPDATE 语句只更新 summary 两列——不 touch `update_time`（时间线不被后台任务推后），带 `status='ACTIVE'` 条件（提交到执行之间会话可能被软删，已删会话命中 0 行，与 touch 先例同构）。

**回滚**：回退代码即可，两列保留无副作用（无人读写）；如需彻底清理可 `DROP COLUMN`，非必须。

### 4.3 边界与合并（核心算法）

1. 读会话全部消息，按与回放完全相同的规则装配完整轮序列（USER+ASSISTANT 双 DONE、rule 轮整轮跳过）——保证被裁检测与回放装配对「完整轮」的判定永远一致。
2. 实算回放窗口起点；窗口外最旧连续段即被裁前缀，其最后一个 roundId 为新边界。
3. 新边界与库中已存边界相同 → 幂等出口。
4. 合并输入 = 现有摘要（如有）+ 边界之后的被裁轮次原文（天然覆盖「配置调小产生的间隙轮」）。
5. 调模型生成新摘要 → 硬截断到 500 字符 → summary 与边界原子更新同一行。

被裁轮次恒为最旧连续前缀是「单边界 roundId」成立的前提（两个上限丢弃方向一致，ADR-0020）。

### 4.4 触发与并发

- 触发点：一轮回答正常收尾（SSE done 已发、emitter 已 complete）后，回答工作线程释放会话锁之后提交异步任务；触发不区分路由类型，rule 轮检测到边界未变走幂等出口。
- 摘要任务 `tryAcquire` 会话锁：拿不到则本轮跳过；边界未推进，下轮完成后的检测重新发现同一被裁前缀，天然幂等重试。
- **已知取舍**：摘要先拿到锁执行期间（模型调用 + 写回，≤10s）用户追问会得到一次 409——保留锁方案（2026-11-26 用户决策），不为摘要引入锁中断复杂度。
- 独立小型单线程池（`ThreadPoolFactory` 装配，有界队列，拒绝时静默跳过）。

### 4.5 注入规则

- 判定落点在 `ConversationHistoryAssembler`：仅当库中边界轮**严格早于**本轮窗口最旧轮才返回摘要正文，否则 null（宁缺勿重；边界轮不在完整轮序列时按不可注入处理）。
- 编排层把返回值拼进 KNOWLEDGE 轮 system 段尾部。
- **两段新 prompt（摘要生成指令、注入块文案）落点 `QaPrompts` 常量类**（面向问答链路的 prompt 集中定义），注入文案显式声明「仅作背景参考」；`QaPromptsContractTest` 逐字断言同步。
- 摘要 prompt 与问答铁律同构（只依据输入、不编造）。
- 摘要不计入 `history-max-chars` 预算；不参与检索 query 改写与路由判定；PLAN 轮不注入。

### 4.6 接口契约

历史消息接口（GET /api/conversations/{conversationId}/messages）响应新增：

- `summary`：摘要正文，无摘要为 null。
- `summaryBoundaryRoundId`：边界轮 id，无摘要为 null。

其余结构不变；前端以 `summary` 非空作为提示条显示条件。

### 4.7 配置项

| 配置 | 默认 | 说明 |
|---|---|---|
| `rag.qa.history-max-rounds` | 10 | 需求 1 定稿值（原 6） |
| `rag.qa.history-max-chars` | 8000 | 需求 1 定稿值（原 2000；成本上限的唯一旋钮） |
| `rag.qa.summary.max-chars` | 500 | 摘要正文独立上限，硬截断 |

不设摘要总开关（用户决策）：失败本身静默降级，开关只会引入状态组合复杂度。

## 5. 测试决策（Testing Decisions）

### 5.1 什么算好测试

只验证对外可观察行为：接口响应字段、装配结果的轮次与摘要内容、库中最终状态（summary 与边界值）、失败路径的降级表现。不验证私有方法与内部调用次数。

### 5.2 采用的测试缝（请评审时确认）

全部复用现有缝，不新增测试基础设施，理想数量为两个：

1. **HTTP 接口层（最高缝）**：历史消息接口控制器测试——summary 两字段的有/无/null 三态、其余结构不变。
2. **服务层单测**：装配器的窗口实算（轮数上限先到 / 字符预算先到 / 混合）、注入判定（严格早于才注入、边界回归窗口时不注入）、合并算法（幂等出口、间隙轮补齐、失败保留旧摘要）。

### 5.3 先例

| 测试对象 | 先例 |
|---|---|
| 装配器行为 | 现有 `ConversationHistoryAssembler` 单测（改签名同步既有用例） |
| schema 两列 | 现有 `SchemaContractTest`，断言点：两列存在与类型、两条幂等迁移语句、两条 `COMMENT ON COLUMN`、`scene` COMMENT 含 `summary` |
| prompt 文案 | 现有 `QaPromptsContractTest`（两段新 prompt 逐字断言同步） |
| Mapper XML | 现有 Mapper XML 契约测试 |
| 控制器出参 | 现有控制器契约测试 |

### 5.4 不做的测试

- 不测真模型调用（摘要客户端用桩）；熔断/留痕行为由 `ResilientLlmExecutor` 既有测试覆盖。
- 不测异步线程池本身，只测「锁被占时跳过、边界不推进」的可观察结果。

## 6. 范围外（Out of Scope）

- 跨会话用户记忆（需求 3）、历史问答向量化检索（需求 4）。
- 摘要参与检索 query 改写或路由判定；PLAN 轮摘要注入。
- 摘要超限的二次生成（只硬截断）。
- 多实例部署下的摘要任务互斥（与回答锁同一限制，单实例进程内生效）。
- 前端提示条交互（点击展开原文等），本期仅展示。
- 窗口参数的进一步再分析与调整（10/8000 已定稿）。
