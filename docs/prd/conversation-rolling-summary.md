# 会话级滚动摘要 · 后端需求文档

> 状态：已定稿（2026-11-26 拷问会收敛，Q1–Q5 全部按推荐口径落地；2026-11-26 二次修订：去掉摘要开关、更正上下文窗口口径）
> 范围：`lender-assistant` 后端
> 来源：需求清单 `E:\ai实际应用\ai-融资智能工作台前后端需求清单.md` 需求 2（需求 1 上下文窗口已定 **10 轮 / 8000 字符**，随本 PRD 一起落地，见 §6）
> 术语口径以 `GLOSSARY.md`「多轮对话词」为准：回放窗口、完整轮、滚动摘要、摘要覆盖边界；决策依据见 [ADR-0020](../adr/0020-rolling-summary-boundary-as-round-id.md)。

## 1. 目标与非目标

### 1.1 目标

1. 会话超过回放窗口后，模型仍能看到「全会话梗概（摘要）+ 最近窗口轮次原文」，早期信息不再无声消失。
2. 摘要覆盖范围**精确到轮次**：库中记录「摘要覆盖到的最后一个完整轮」的 `roundId`，不假设固定轮数。
3. 用户可见性：历史消息接口带出摘要元信息，前端在消息列表顶部展示轻量提示条（仅展示、无交互）。

### 1.2 非目标（本次不做）

- 跨会话用户记忆（需求 3）、历史问答向量化检索（需求 4）。
- 上下文窗口参数调优的再分析（需求 1 已定：10 轮 / 8000 字符，见 §6，不再讨论）。
- 摘要参与检索 query 改写或路由判定（检索 query 仍用历史原文，路由输入不变）。
- PLAN 轮合成的摘要注入（PLAN 合成本就不重放完整历史，保持现状）。
- 多实例部署下的摘要任务互斥（与回答锁同一限制，单实例进程内生效）。

## 2. 核心设计决策（拷问会结论）

### 2.1 边界必须动态实算，禁止引用配置数字（Q2）

回放窗口实际保留轮数 = `min(轮数上限, 字符预算允许的轮数)`：短追问会话能保满轮数上限，正常 RAG 回答（每轮 700 字符上下）会更早被字符预算裁剪。因此：

- **触发检测、摘要合并、注入判断全部从 DB 消息实算**，绝不允许出现「第 6 轮之前」这类按配置数字驱动的分支。
- 被裁轮次永远是完整轮序列的**最旧连续前缀**（两个上限的丢弃方向一致），这是「单边界 roundId」成立的前提。

### 2.2 摘要覆盖边界落库（Q1）

`conversation` 表新增两列：

| 列 | 类型 | 含义 |
|---|---|---|
| `summary` | TEXT NULL | 滚动摘要正文；NULL 表示尚无摘要 |
| `summary_boundary_round_id` | TEXT NULL | 被摘要覆盖到的**最后一个完整轮**的 `roundId`；与 summary 同写同空 |

存量库走幂等 `ADD COLUMN IF NOT EXISTS` 迁移（与 route / execution_plan 先例一致），schema 变更同步回写 `docs/schema.sql`（§6.8），每列带 `COMMENT ON COLUMN`（schema.sql 惯例）。

**写回规则**：摘要写回用独立 UPDATE 语句，只更新 summary 两列——**不 touch `update_time`**（会话列表时间线不被后台任务推后），且带 `status='ACTIVE'` 条件（提交到执行之间会话可能被软删，已删会话命中 0 行，与 touch 先例同构）。

### 2.3 窗口配置变更的两个方向（Q3）

消息全量落库、窗口只是回放策略——这是两条规则的共同前提：

- **改小（如未来 6→4）**：出现「已摘要边界 < 新窗口最旧轮」的**间隙轮**（被新裁掉但摘要没盖住）。规则：下次合并时把间隙轮原文从 DB 取出，连同现有摘要一起滚动合并。无信息丢失，代价只是多一次合并调用。
- **改大（如未来 6→10）**：被摘要覆盖的旧轮从 DB **自然回归窗口**，不做任何追加动作；但会与已注入摘要**重复**。规则：注入前检查——仅当 `summary_boundary` 轮**严格早于**本轮窗口最旧轮时才注入，否则本轮跳过注入（宁缺勿重）。当这些轮再次被裁出时，照常并入摘要。

### 2.4 触发时机与并发（Q4）

- 触发点：一轮回答**正常收尾后**（SSE `done` 已发、emitter 已 complete），在回答工作线程释放会话锁之后提交异步摘要任务。**触发不区分路由类型**：rule 轮收尾同样提交，检测到边界未变走幂等出口。
- 摘要任务 `tryAcquire` 会话锁：拿不到（新一轮正在回答）→ 本轮跳过。跳过无害：边界未推进，下一轮完成后的检测会重新发现同样的被裁前缀，**天然幂等重试**。
- **已知取舍（反方向）**：摘要先拿到锁执行期间（模型调用 + 写回，上限约 10s）用户追问会得到一次 `CONVERSATION_BUSY`(409)。保留锁方案（2026-11-26 用户决策）：摘要与回答互斥语义简单，短暂忙碌可接受，不为摘要引入锁中断或抢占复杂度。
- 摘要任务独占一个小型单线程池（`ThreadPoolFactory` 装配，有界队列，拒绝时静默跳过），摘要慢不反压回答主链路。

### 2.5 摘要调用规格（Q5）

- 非流式调用，新增 `LlmScene.SUMMARY`（scene 取值清单同步 `llm_call_log.scene` 注释）。
- 走 `ResilientLlmExecutor`：留痕 + 熔断 + 重试（非流式 allowRetry=true），与路由调用同构；超时与路由/计划客户端同构——Reactor `timeout` 复用代码常量 `NON_STREAM_TIMEOUT`（10s），不新增配置项（摘要失败静默降级、下轮幂等补齐，更长超时无收益）。
- 调用走 `conversation/client/` 层（§0.2 外部模型网关规则、清单红线）。
- 摘要正文上限 **500 字符**（`rag.qa.summary.max-chars`，默认 500），超限**硬截断**——摘要只是背景参考，截断断句可接受，不为此追加二次模型调用。
- **摘要不计入 `history-max-chars` 预算**：该预算管原文回放窗口，摘要有独立上限。
- 生成失败**静默降级**：保留旧摘要（边界不推进），记 WARN 日志，不挡主链路。

## 3. 注入规则

- 注入位置：KNOWLEDGE 轮的 system 段尾部追加摘要块（`QaPrompts.summaryBlock`），渲染形如：

  ```
  【更早对话摘要】以下是本会话回放窗口之外更早轮次的梗概，仅作背景参考：
  <summary>
  ```

- 判定落点在 `ConversationHistoryAssembler`（清单约束）：装配时读会话摘要，满足「边界轮严格早于窗口最旧轮」才返回非空摘要；编排层只负责把返回值拼进 system prompt。
- 摘要是模型生成的内容，属治幻觉体系的新增面，故摘要 prompt 有与问答同构的铁律（只依据输入、不编造），且注入文案显式声明「仅作背景参考」。

## 4. 滚动合并算法

检测与合并一次完成（单线程串行，无并发窗口）：

1. 读该会话全部消息，装配出**完整轮序列**（USER+ASSISTANT 双 DONE、rule 轮整轮跳过，与回放同一套规则）。
2. 实算回放窗口起点；窗口外的最旧连续段即**被裁前缀**，其最后一个 `roundId` 为新边界。
3. 新边界与库中已存边界相同 → 无新增被裁轮次，结束（幂等出口）。
4. 合并输入 = 现有摘要（如有）+ **边界之后**的被裁轮次原文（含间隙轮，即 2.3 改小场景的补齐）。
5. 调模型生成新摘要 → 硬截断到 500 字符 → `summary` 与 `summary_boundary_round_id` 原子更新同一行。

## 5. 对外契约变更

### 5.1 历史消息接口（GET /api/conversations/{conversationId}/messages）

响应新增两个字段：

```json
{
  "conversationId": "...",
  "summary": "用户在会话早期确认关注华信租赁的小额产品线……",
  "summaryBoundaryRoundId": "7d0f...",
  "messages": [ ... 原有结构不变 ... ]
}
```

- 未生成过摘要的会话两字段为 `null`——前端据 `summary` 非空决定是否显示提示条，未超窗口的会话天然无摘要、不出现提示条（验收口径）。

## 6. 配置

```yaml
rag:
  qa:
    # 需求 1（2026-11-26 定稿）：由 6 轮 / 2000 字符调整为如下值
    # 追问回放给模型的历史上限：最近 10 个完整轮次、总字符 8000
    # （≈4800 token，占 deepseek-chat 128K 窗口 <4%；8000 字符是成本上限，短期会话按实际字数计费不增加；
    #   多轮历史逐字追加，命中前缀缓存后常态成本接近零。进一步控成本降字符预算，不降轮数）
    history-max-rounds: ${RAG_QA_HISTORY_MAX_ROUNDS:10}
    history-max-chars: ${RAG_QA_HISTORY_MAX_CHARS:8000}
    # 需求 2：摘要正文独立上限，不计入 history-max-chars 预算
    summary:
      max-chars: ${RAG_QA_SUMMARY_MAX_CHARS:500}
```

## 7. 验收

1. 15 轮会话（正常 RAG 回答长度），第 1 轮提到的关键事实（如客户号、产品编码）在第 15 轮追问时仍被正确引用，且引用内容可溯源到摘要注入。
2. 超过窗口的会话历史接口返回非空 `summary`，前端顶部出现提示条；未超窗口会话两字段为 null、无提示条。
3. 摘要任务拿不到锁时跳过让路：用户追问不撞 `CONVERSATION_BUSY`；摘要**持锁执行期间**（≤10s）追问会得到一次 409，属已知取舍（PRD §2.4）；被跳过的摘要下一轮回答完成后补齐。
4. 模型故障（chaos 或熔断）时：回答链路完全无感，`llm_call_log` 出现 `scene=summary` 的 FAIL 行，库中旧摘要保留。
5. `mvn test` 全绿；`SchemaContractTest` 断言两列与幂等迁移语句已声明。

## 8. 风险与红线自查

- **摘要丢细节导致答非所问** → 摘要只做背景补充，检索 query 仍用历史原文；注入文案显式声明参考性质。
- **摘要错误扩散** → 摘要 prompt 铁律只依据输入；用户删除会话即丢弃摘要，无跨会话传播。
- **红线**：摘要调用走 `client/` 层并留痕（§5.3）；摘要生成不在事务内做（§6.11）；线程池走 `ThreadPoolFactory`（§7.1）；schema 回写 `docs/schema.sql`（§6.8）。
