# 阶段 2：问答链路 v1（设计稿）

> 状态：⬜ **未实施**。本文档是开工前的设计约定，实施时如有出入，以代码实际为准并回改本文。
> 手册验收标准：5 个真实业务问题，回答基本正确。

## 一、目标

把阶段 1 的"检索"升级为"问答"：

```
用户问题 ──> SearchService.hybridSearch(topK) ──> 拼 Prompt（只准依据召回内容回答）
         ──> DeepSeek 生成 ──> SSE 流式返回前端
```

前置依赖：DeepSeek API key（或先用 Mock 对话模型开发，见第五节）。

## 二、新增/改动模块

| 模块 | 职责 |
|---|---|
| `service/QaService`（新增） | 编排：检索 → 组装 Prompt → 调对话模型 → 流式输出 |
| `controller/QaController`（新增） | `POST /api/qa`，返回 `text/event-stream`（SSE） |
| `ChatService` | 阶段 0 的最简对话，阶段 2 起改造为 RAG 问答的模型调用层 |
| `SearchService` | 顺手修关键词通道：整句 trigram → **分词后多词 OR 匹配**（阶段 1 已知短板） |
| `index.html` | 加对话区：调 `/api/qa` 消费 SSE |

## 三、Prompt 设计（核心约定）

系统提示词三条铁律（面试可讲）：
1. **只依据召回内容回答**，召回内容不足以回答时明确说"资料中未提及"，禁止编造——RAG 的价值就在于把模型的"幻觉面"压到召回质量上
2. 回答末尾标注**引用来源**（docTitle + sectionPath），为阶段 3 的引用溯源打底
3. 问题涉及具体字段/格式时优先引用表格原文

召回内容注入格式：每条 chunk 带 `【来源 N：docTitle / sectionPath】` 头，模型回答时引用"【来源 N】"。

## 四、SSE 技术选型

用 Spring MVC 的 `SseEmitter`（不引 WebFlux）：
- 项目是 spring-boot-starter-web（Servlet 栈），为一条流式接口引 Reactor 不值
- Spring AI 的 `ChatClient.stream()` 返回 Flux，用 `doOnNext` 往 SseEmitter 写、`doOnComplete` 收尾即可，Flux 只在服务内部存活
- 前端用原生 `EventSource` 或 `fetch + ReadableStream` 消费

## 五、无 key 开发策略（延续阶段 1 思路）

对话模型同样抽成可替换口：DeepSeek 走 Spring AI starter；key 未配置时装配一个 `MockChatModel`（把召回 chunks 的摘要拼成"回答"返回），保证**整条 SSE 管道可开发、可调试**。key 到位后切真实模型，一行业务代码不动。

## 六、验收用例（5 个，验收时逐条记录）

5. 借据编号的字段类型和长度？（问一份文档里没有的内容，**预期回答"资料中未提及"**——验证铁律 1）
