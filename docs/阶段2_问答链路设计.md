## 三、Prompt 设计（核心约定）

系统提示词三条铁律（面试可讲）：
1. **只依据召回内容回答**，召回内容不足以回答时明确说"资料中未提及"，禁止编造——RAG 的价值就在于把模型的"幻觉面"压到召回质量上
2. 回答末尾标注**引用来源**（docTitle + sectionPath），为阶段 3 的引用溯源打底
3. 问题涉及具体字段/格式时优先引用表格原文

召回内容注入格式：每条 chunk 带 `【来源 N：docTitle / sectionPath】` 头，模型回答时引用"【来源 N】"。

## 四、SSE 技术选型

用 Spring MVC 的 `SseEmitter`（不引 WebFlux）：
- 项目是 spring-boot-starter-web（Servlet 栈），为一条流式接口引 Reactor 不值
- Spring AI 的 `ChatClient.stream()` 返回 Flux，用 `doOnNext` 往 SseEmitter 写、`doOnComplete` 收尾即可，Flux 只在服务内部存活
- 前端用原生 `EventSource` 或 `fetch + ReadableStream` 消费

### 4.1 真流式的关键：立即返回 emitter + 独立线程 send（2026-10-17 修复）

`QaService.answer()` 必须**立即 `return emitter`**，把检索 / 生成 / `send` 全部放到独立工作线程（`streamExecutor`）执行：

- **反面写法**（在请求线程内 send）：`ResponseBodyEmitter` 在控制器尚未返回、handler 还没挂上时，会把 `send()` 的数据先堆进 `earlySendAttempts` 缓冲，直到控制器返回才一次性 flush → **TTFB ≈ 总耗时**的"假流式"；突发写完立刻断连还会让 Chrome 记 `net::ERR_ABORTED`。
- **正确写法**：`streamExecutor.execute(() -> streamAnswer(emitter, ...)); return emitter;`——handler 先挂上，之后的每次 `send` 都是即时 flush。
- 实测（Mock 12 字/30ms）：修复前 `curl -w` 的 `time_starttransfer=2.830s` ≈ `time_total=2.844s`；修复后 `TTFB=0.556s` / `total=3.557s`，确证真流式生效。
- 线程池固定 8、daemon 线程、`@PreDestroy` 时 `shutdownNow()`——避免 SSE 长连接导致线程无界膨胀，且不阻塞 JVM 退出。

> 排障提示：`net::ERR_ABORTED http://localhost:8080/api/qa` 若只出现在 **Trae 内置预览**里，是预览层代理缓冲所致（抓包证实服务端响应规范完整、末尾 `event:done` + `0\r\n\r\n` 终止块齐全、curl 能收全），换**普通浏览器**访问即正常，应用侧无需改动。
