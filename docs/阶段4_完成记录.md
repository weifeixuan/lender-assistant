## 四、验收过程发现并修复的真问题

这正是"先验收再写文档"的价值——三个都是测试/演示环境里才暴露的：

1. **映射残留脏数据（本次修复）**：`saveMappings` 只 upsert 不清理，重抽后消失的字段映射永远留在库里（huaxin 库里残留 2 条误报时代的旧数据）。修复：重抽前先 `DELETE ... WHERE doc_id=? AND status='PENDING'`，人工确认行（CONFIRMED/CORRECTED）绝不动——真库验证 CORRECTED 行重抽后完好。49 tests green。
2. **章节标题不在 content 里**（part1 期间）：`SectionSplitter` 只把标题存 `section_path`，抽取器按 content 找标题永远落空。修法：`loadDocContent` 拼全文时每个 chunk 前置【章节】行。
3. **状态枚举被 chunk 边界切残**（part1 期间）：`SUCCESS / FAILED / PROCESSING` 被切成 `SUCCESS / FAIL`，首匹配抽到残值 → 改最长匹配。

## 五、设计决策备忘（为什么）

- **熔断器用纯库编程式**（`CircuitBreaker.decorateSupplier`）而非 Spring 注解：单测不起容器就能驱动状态机红绿循环（OPEN 后快速失败、业务零调用都有断言）。
- **装饰层顺序 CB 在外 Retry 在内**：重试的每次尝试都计入熔断失败统计，避免"重试掩盖故障导致熔断永不打开"。
- **SSE 问答禁重试**：token 已推给用户，重放就是重复播报事故；抽取是非流式一锤子调用，可安全重试。
- **不引 TimeLimiter**：超时已由 DeepSeek 流 `.timeout(60s)` + SseEmitter 120s 兜底覆盖，当前规模加 TimeLimiter 是过度设计。
- **Mock 的 Function Calling 是规则模拟**：`ToolIntentRouter` 关键词路由 + 惰性求值 docId 清单（普通问题零额外查询）；DeepSeek 版走 Spring AI `.tools()` 让模型真决策。两条路共享同一套工具实现。
