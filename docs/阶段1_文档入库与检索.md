## 一、数据流总览

```
上传 docx ──> DocxParser ──> ParsedDocument(带标题层级 Block) ──> SectionSplitter ──> Chunk 列表
                                                                        │
                        入库统计返回 <── DocumentStore <── EmbeddingClient (hash | zhipu)
                                                                        │
                检索请求 ──> SearchService ──> 向量通道(HNSW) + 关键词通道(trigram) 合并排序
```

分层原则：**每层都是接口 + 可替换实现**——这是"key 后补也能开发"能成立的架构原因。

| 接口 | 实现 | 切换方式 |
|---|---|---|
| `DocumentParser` | `TextParser`(.txt/.md)、`DocxParser`(POI，保留标题层级与表格文本) | 按 `supports(fileName)` 自动路由 |
| `ChunkSplitter` | `SectionSplitter`(按标题段落)、`FixedSizeSplitter`(固定字数+重叠窗口) | 配置 `rag.split.strategy` |
| `EmbeddingClient` | `HashEmbeddingClient`(Mock)、`ZhipuEmbeddingClient`(真实，key 缺失不装配) | 配置 `rag.embedding.provider` |

## 二、表结构（`docs/schema_phase1.sql`）

核心表 `doc_chunk`：
- `embedding VECTOR(1024)`——智谱 embedding-3 原生 2048 维，API 支持降维；存储减半、HNSW 更快，召回率损失留到阶段 3 实测对比（这就是简历素材）
- HNSW 索引（向量）+ trigram 索引（关键词）——**混合检索**的物理基础
- `UNIQUE(doc_id, chunk_index)`——重复入库先删后插的幂等保障，切分策略反复实验不攒脏数据

## 三、关键设计决策（面试追问点）

1. **Hash 向量的原理与边界**：中文 bigram + ASCII 词分词，`String.hashCode()` 投桶（JLS 规范定义，跨 JVM 确定性），L2 归一化。它能验证**链路正确性**，不能评估**语义检索效果**——"逾期"和"过期末还"在 hash 世界里毫无关系。阶段 3 的效果数字必须换真向量后测。
2. **切分时把 sectionPath 拼进向量化输入**（`DocumentAdminController.upload`）：标题"3 逾期文件"是强语义信号，不拼进去向量就不知道这段在讲什么主题。
3. **JdbcTemplate + 手写 SQL，不用 JPA**：`<=>`（余弦距离）、`::vector` 类型转换、`SIMILARITY()` 全是 PG/pgvector 扩展语法，JPA 表达不了。
4. **HNSW 而非 IVFFlat**：IVFFlat 建索引需要表里先有数据做聚类中心；HNSW 随时可建、查询延迟稳定，个人项目数据量下无脑选它。
5. **`FixedSizeSplitter` 的重叠窗口**（overlap=100）：被 chunk 边界斩断的语义单元会在下一块开头补全，用冗余换覆盖率。
