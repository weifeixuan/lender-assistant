## 二、指标选择（面试可讲）

- **recall@K 而非 precision**：问答场景里检索的职责是"把相关内容送进 Prompt"，漏了就答不出；topK 只有 4 条，多几条噪声模型自己会过滤，所以优化目标是大召回。
- **MRR 补排名信息**：recall 只看"命中没有"，MRR 看第一名命中排多前——Prompt 预算有限，好结果排在第 1 和第 4 的价值完全不同。
- **ground truth 用关键词判定**：`mustContain` 任一命中即相关。对字段名/路径/格式串这类 FACT/RULE 问题足够准；"回答是否正确"的语义判定属生成质量评估，不在本脚本职责内。

## 三、调优闭环（本阶段的核心故事）

1. **三模式基线**：hybrid 94.7% / vector 100% / keyword 94.7%——vector 竟然最高，可疑；
2. **定位**：用例 8（时间戳格式）在 vector 里排第 1，hybrid 里掉出 top4——v1 硬排序（双通道优先）让关键词通道的宽泛命中挤掉了向量通道的头名；
3. **改 RRF**：score = Σ 1/(K+rank)，K=60，按排名平滑融合、不偏袒通道；
4. **复测**：hybrid recall 94.7%→**100%**，MRR 0.860→**0.877**，其余用例零回退。

**插曲（评估框架价值的现场证明）**：第一版 RRF 把排序方向写反（`Double.compare` 升序），recall 立刻崩到 52.6%——两分钟定位两分钟修复，这正是"有评估集"和"没评估集"的区别：没有它，这个 bug 会静默活在生产路径里。
